- [x] Find a way to keep the dependency source code out of the repository to reduce noise - the dependencies are resolved by Conan when the addon is built, only the GDAL and PROJ data files and the curl root certificates are still shipped in `deps/`
- [x] Switch to cmake.js - the addon is built from `CMakeLists.txt`, `binding.gyp` and node-gyp have been removed
- [x] Switch from nan to N-API - the addon uses node-addon-api and a single `napi-v8-{platform}-{arch}` binary is published per platform
- [x] Support aborting of GDAL operations (that allow it) through the AbortController (Node.js >= 15) - the long-running operations accept an `abort_signal` option and fail with an `AbortError`; only the operations which support progress callbacks can be interrupted, and only in their asynchronous form
- [x] Support `worker_threads` (almost automatic with N-API) - each thread gets its own Node-API environment and its own object store
- [x] Give every Node-API environment a single context object instead of the current set of `thread_local` variables - `EnvContext` holds the object store, the interned private symbols, the constructor reference of every wrapped class, the pointer hand-off slot of the wrapper factories and the flag which says that the environment is shutting down. It is found through the environment it belongs to, so two loadings of the addon in one process (CJS + ESM) share it, and it outlives the environment, because V8 finalizes the objects which are still alive after the environment cleanup hooks have run
- [x] Replace the hand-rolled `this_` + `owned_` ownership of the wrapped objects with a typed handle whose deleter is fixed at construction - `Handle<T>` (`src/utils/handle.hpp`) keeps the pointer together with the function which frees it, or with no function at all for the objects a parent owns. The classes which own their object (`FieldDefn`, `FeatureDefn`, `Feature`, `SpatialReference`, `Geometry`, `CoordinateTransformation`, `ColorTable`) get the handle from their factory, so there is no flag to forget and the question of who frees what is answered once, where the object is created. `Dataset`, `RasterBand`, `Layer` and `Driver` only borrow their object, because the object store frees those
- [x] Replace the 297 `NODE_ARG_*` uses and the 93 `GDAL_ASYNCABLE_DEFINE` macro definitions with a declarative argument binder and an `AsyncMethod<Impl>` template. One macro expansion per method generates the synchronous *and* the asynchronous variant, and each argument check throws from inside the argument list itself (478 `ThrowAsJavaScriptException`), which is where the "an exception thrown inside a `try` block is swallowed by the `catch (const std::exception &)`" trap lives. The `@param` doc comments stay - yatag parses those, not the macro calls
- [x] Carry the failures in a `GDALError`, a message together with the name and the code of the error it has to become, instead of a bare `const char *`, and build the JS error in a single place (`toJS()`/`throwError()`). The asynchronous worker has one boundary which turns whatever its `Execute()` caught into a JS error, the `AbortError` is no longer built at every call site, and only the `GDALAbortState::interrupted` flag can turn a failure into one, so a genuine GDAL error which happens to arrive after an abort is still reported as itself
- [x] Write every method once, as a body which generates both the synchronous and the asynchronous variant - every method is a body struct behind a single `GDAL_ASYNC_METHOD`/`GDAL_ASYNC_GETTER`/`GDAL_ASYNC_METHOD_STATIC`/`GDAL_SYNC_METHOD`/`GDAL_SYNC_GETTER` expansion, so the two forms of a method are the same code and cannot drift apart. The body takes its arguments from `Args`, checks that `this` is still alive with `unwrapThis()` - which throws in the synchronous form and rejects in the asynchronous one, because a throw from a getter would reach the caller instead of the promise - and ends with `job.run(info, node_gdal::is_async<Async>, cb_arg)` when it has an asynchronous variant. The thirty `NODE_WRAPPED_METHOD*` and `NODE_WRAPPED_GETTER*` macros are gone, `src/gdal_common.hpp` is down to 39 macros, and it keeps only the throwing helpers, the unwrapping checks, the optional argument conversion and the constants
- [x] Make the objects which a parent owns throw when they are written to, instead of silently writing into a clone - `layer.fields.get('x').width = 3`, `feature.defn.geomType = ...` and `layer.srs.setWellKnownGeogCS(...)` used to succeed and change nothing, because the getters hand out copies. The copy is now marked read-only, with a private symbol on the wrapper (`set_read_only()`/`is_read_only()` in `src/gdal_common.hpp`), and every write to one is refused with a `read-only, create a new one to modify it` error: the `FieldDefn` of `Layer.fields` and of a feature definition, the `FeatureDefn` of `Feature.defn` together with its `fields` collection, the `SpatialReference` of `Layer.srs`, of `Geometry.srs` and of the multidim objects, and the `ColorTable` of a band, which already refused to be written to with a message of its own. A copy stays a copy - `clone()` hands out an object which can be modified, and a spatial reference which is already wrapped is handed out as itself, so `geom.srs` is still writable when it is the very object which was assigned to the geometry
- [x] Tell V8 about the memory GDAL holds on our behalf - `AdjustExternalMemory` was called for the geometries and the mem files only, so a process which has opened a hundred datasets looked idle to the garbage collector, which then had no reason to run and collect the wrappers nobody uses. The accounting now belongs to `GDALObject`, as `setExternalMemory()`, and the base destructor gives back whatever a wrapper still holds, so the classes which own memory only have to say how much it is: a `Dataset` reports the blocks of its bands, or the whole raster when it is a MEM dataset, and is re-reported when a band is added to it, a `Feature` reports the size of the geometries it carries, both when it is created and when its geometry is replaced, and the geometries and the mem files report what they already did. The estimate is deliberately on the low side, since a driver keeps its own caches out of reach, and it cannot be asserted from JavaScript - the counter is not visible to `v8.getHeapStatistics()` - so the tests only check that nothing reports so much that the suite is slowed down.
- [x] Keep one source of truth per method: the registration - the same fact was written four times, as the argument binder in C++, as the `@param` comment which yatag reads, as the 11,121 lines of `lib/index.d.ts` and as the `promisifiables` and `argMangle` tables in `lib/gdal.js`, and nothing checked that they agree. `test/api_registration.test.ts` now parses the registration out of `src/` - the `GDALDefineClass<>` descriptor lists and the `GDAL_SetMethod`/`GDAL_SetAsyncableMethod` calls of every `Initialize` - and fails when a registered member has no `@method`/`@name` comment of its class or of one of its ancestors, when a comment survives the member it documents, or when the typings do not declare it. The typings are generated from those comments by `npm run yatag`, so what is documented is typed, and the check found the drift which was there: `SpatialReference.isVectical`, which the registration exposes but nothing documented, `LinearRing.addSubLineString`, a registration which shadowed the inherited `SimpleCurve` method and with it its memory accounting, and the unregistered implementations of `Feature.equals` and `Geometry.create` with their doc comments
- [x] Return the promise from the binding instead of wrapping it in JavaScript - `GDALAsyncableJob::run` already knew at which argument the callback goes, yet `lib/gdal.js` kept a table of 110 `xAsync` to callback index entries in order to promisify the methods. Now an asynchronous method returns the promise itself when the call has no callback: `AsyncMethod<Body>` looks for the callback at the argument the body declared or as the last argument of the call, and a failure which happens before the job starts rejects that promise instead of being thrown at the caller. The table and the `argMangle` map are gone, `Args::optionalCallback` reports the raw index so that the callback is the one argument the binder does not consume, and the 103 asynchronous methods - the ones which take a callback and the getters, which never do - work without a JavaScript wrapper
- [x] Catch up with the modern Node.js surface - a `Dataset` has `Symbol.dispose` and `Symbol.asyncDispose`, so `await using ds = await gdal.openAsync(...)` closes the dataset when the block ends, even if it throws; the two members cannot be generated by yatag, which drops the brackets of a member name and would emit `Symbol.dispose()` - not valid TypeScript - so they are filtered out of the generated interfaces and declared by the `footer` of `yatag.config.js` instead. `package.json` has an `exports` map, so an ESM consumer resolves the package with the standard rules instead of the interop ones, while the root import and the deep imports under `lib/` keep working, and `engines` says Node.js 22, which is the oldest version which is still supported
- [x] Teach the argument binder the flexible shapes of the pixel arguments - `RasterBandPixels.read`/`write` had their arguments flattened into a positional list by `mangleRead`/`mangleWrite` in `lib/gdal.js`; the body now reads the five positional arguments and the trailing options object itself, with the same `Args::from()` which the multidim methods already used, and `readBlock`/`writeBlock`/`MDArray.read` lost the type hint which JavaScript used to write onto the buffer. The data type of a `TypedArray` is read from the array itself - `TypedArray::Identify()` maps the N-API type of the view, including `Float16Array` on Node.js 24 - so the only one which still needs help is the polyfilled `Float16Array` of Node.js < 24, which is not an `ArrayBufferView` at all: `lib/gdal.js` hands it over as a `DataView` tagged with the data type of its elements, and that wrapper disappears together with the polyfill. `wrapMangled`, the four manglers and the internal positional `AbortSignal` (`NODE_ABORT_SIGNAL_FROM_ARG_OPT`) are gone, so `Args` is the only place which knows what the arguments of a method mean
- [x] Let the band statistics report their progress and be interrupted - `RasterBand.computeStatistics` was the only operation which scans a whole raster and passed `NULL` for the progress function of GDAL, so it could neither report how far it had got nor be aborted, while every other long-running method had both. It now takes the same trailing options object, with `progress_cb` and `abort_signal`, and `NODE_PROGRESS_CB_OPT` accepts a function in the place of that object as the callback of a method whose options are optional instead of refusing it as "options must be an object" - which is what made the older call `computeStatisticsAsync(true, callback)` keep working. The audit which found it is the point: every method which accepts an `abort_signal` is one which hands a progress function to GDAL, so a new long-running method which passes `nullptr` there is the only way to have an operation which cannot be interrupted
- [x] Drop the global error handler which serialized the band statistics - `computeStatistics` cannot take its errors from `CPLGetLastErrorMsg()`, because `GDALComputeRasterStatistics` reports the failures of the four statistics it reads through the error handler, so `src/gdal_rasterband.cpp` replaced the global handler, collected the message in a global `stats_file_err` and guarded the whole computation with a global `stats_lock`. Two statistics of two different datasets waited for each other for the duration of the raster scan, and the message outlived the computation which produced it: nothing ever cleared it, so the first VRT whose source could not be opened made every later statistics call of the process - including the `getStatistics` of a perfectly healthy band - fail with its error. The handler now goes on the thread-local stack of GDAL (`CPLPushErrorHandler`/`CPLPopErrorHandler`) with thread-local storage for the message, which is cleared before every computation, so the mutex is gone, two datasets report their progress at the same time, and each computation reports its own error
- [x] Generate `lib/default_iterators.js` with a script of our own instead of with `gpp` - the template uses a handful of `<#define name|body>` blocks which are instantiated with `<#name arg1|arg2|arg3|arg4>`, and `gpp` is an external C program which was not a dependency of the package, had no pinned version and could not be installed on every platform we build on, so the file in the repository and the file in a build could disagree with nothing to notice. `scripts/generate-default-iterators.js` expands the same template with the same rules and formats the result with the eslint of the repository, `npm run iterators` regenerates the file, and `npm test` - which every CI job runs - fails with `npm run iterators -- --check` when the committed file is out of date
- [x] Finish the modern surface - the mask flags of `RasterBand` are exposed as `gdal.GMF_ALL_VALID`, `gdal.GMF_PER_DATASET`, `gdal.GMF_ALPHA` and `gdal.GMF_NODATA` instead of being bare numbers and hex values in the documentation, the `srs` getter of a `Geometry` passes the pointer of GDAL to the read-only `SpatialReference::New` overload instead of `const_cast`ing it on the GDAL versions where it is `const`, and the documentation is generated by `typedoc` from `lib/index.d.ts`, the file which `yatag` generates from the same doc comments, replacing `documentation` and its Markdown/Hipster theme which read the method names out of the macros and could no longer see a single one of them - there is no `TODO` comment left in `src/`
- [x] Make the wrapped objects describe themselves when they are printed - `Dataset`, `RasterBand`, `Geometry` and `Feature` have a `Symbol.for('nodejs.util.inspect.custom')` method, so `console.log(dataset)` shows `Dataset { description: "sample.tif", size: [984, 804], bands: 1 }` instead of `Dataset {}`. A closed object cannot be read at all, so the members are read in a `try` and the object describes itself as `<closed Dataset>`; the members of the other classes (`Envelope`, `ColorTable`, `Layer`, ...) are already shown by the default output, so they are left alone
- [x] Give the failures classes - every failure which GDAL reports is a `gdal.GDALError` or one of its subclasses, one per CPLE error number - `gdal.GDALOpenError`, `gdal.GDALFileIOError`, `gdal.GDALUnsupportedError`, `gdal.GDALNoWriteAccessError` and the rest, with the seven `CPLE_AWS*` codes sharing `gdal.GDALAWSError` - so `e instanceof gdal.GDALOpenError` tells a missing file from a refused write, and `e.code` still names the exact CPL code. An interrupted operation is a `gdal.AbortError` with the `ABORT_ERR` code of the Node.js core, and the errors of a bad argument stay the native `TypeError`s and `RangeError`s. `GDALError::fromGDAL()` builds the failure from the last CPL error number, so the 69 call sites which threw `GDALError(CPLGetLastErrorMsg())` keep their message and gain the class, and the classes themselves are set up once per Node-API environment in `initErrorClasses()`
- [x] Give the module a modern surface - the module is still CommonJS, but `lib/gdal.mjs` is the `import` condition of the `exports` map and it re-exports the 66 classes of the API as named exports, so `import { Dataset, RasterBand } from 'gdal-async'` works in an ES module while `import gdal from 'gdal-async'` and `require('gdal-async')` keep working and reach the same objects; the `lib/` files require the core modules with the `node:` prefix, so they cannot be shadowed by a userland package of the same name
- [x] Make the C++ failures flow as exceptions instead of being set as pending exceptions by a macro - `NODE_THROW_LAST_CPLERR` and `NODE_THROW_OGRERR` needed a local variable named `info` and set the JS exception where the failure was noticed, so their 63 call sites could not stop the function from running the rest of its body, and a failure raised in a plain method, in a static method or in a constructor arrived as a generic `Error` because only the body structs of `SyncMethod`/`AsyncMethod` knew about `GDALError`. The two macros are gone and every one of those failures is a `throw GDALError(...)`; the three entry points which cannot let a C++ exception escape are now the only places which build the JS error - the method trampoline routes `GDALError` through `throwError`, the free and static functions go in through `FreeFunctionTrampoline`, and a constructor sets the exception pending and returns, because node-addon-api's wrapper for it catches `Napi::Error` only
- [ ] Trim the macros which only exist to smuggle `info` into a statement - `GDAL_GET_PRIVATE`/`GDAL_SET_PRIVATE` (137 uses) become `getPrivate`/`setPrivate` templates, `IS_WRAPPED`, `ARG_FIELD_ID` and `UPDATE_AMOUNT_OF_GEOMETRY_MEMORY` become functions, and the three dead ones (`METHOD_HIDDEN`, `NODE_DEFINE_CONSTANT_HEX`, `GDAL_HAS_PROP`) go away. The C-isms of the sources go with them: `NULL` becomes `nullptr` and the factories which return a bare pointer are marked `[[nodiscard]]`
- [ ] Replace the unwrap macros with two function templates which throw - `NODE_UNWRAP_CHECK`/`_ASYNC`/`_VOID` and `GDAL_RAW_CHECK`/`_ASYNC`/`_VOID` (129 uses) declare a variable and return on failure, which is the only reason they are macros, and they also need the local variables `info` and `async`; now that a failure is an exception, `unwrapOrThrow<T>(info, "Dataset")` and `rawOrThrow<T>(obj)` do the same job and the bodies stop depending on what the enclosing macro happened to call its variables
